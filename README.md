# Notetaker

Личные заметки с привязкой к дате и времени: календарь (месяц/неделя/день), теги, повторяющиеся заметки, напоминания (email + уведомления в браузере), корзина, поиск и фильтры, экран «Ближайшее», синхронизация между вкладками и устройствами.

- **Backend:** FastAPI, async SQLAlchemy 2 (asyncpg), PostgreSQL 16
- **Frontend:** React (Vite, JavaScript), FullCalendar, luxon
- **Почта для разработки:** Mailpit (SMTP-ловушка с веб-интерфейсом)
- **Запуск:** Docker Compose

## Быстрый старт

### 1. Требования
Docker и Docker Compose v2. Больше ничего ставить не нужно.

### 2. Клонирование
```bash
git clone <url-репозитория> notetaker
cd notetaker
```

### 3. Файл `.env`
Скопируйте шаблон и при необходимости поправьте значения:
```bash
cp .env.example .env
```
Если `.env.example` в репозитории нет, создайте `.env` вручную:
```env
# PostgreSQL
POSTGRES_USER=app_user
POSTGRES_PASSWORD=super_secret_password
POSTGRES_DB=app_db
POSTGRES_PORT=5432

# Приложение (для запуска вне Docker)
DATABASE_URL=postgresql+asyncpg://app_user:super_secret_password@localhost:5432/app_db

# SMTP (в compose указывает на Mailpit)
SMTP_HOST=mailpit
SMTP_PORT=1025
SMTP_FROM=notetaker@example.com
```
Остальные переменные (секрет подписи токенов и т.п.) смотрите в `app/config.py`: у всех, что обязательны, нет значения по умолчанию. Файл `.env` не коммитится (он в `.gitignore`), в репозитории лежит только `.env.example`.

> В продакшене обязательно замените пароль БД и секреты и подключите реальный SMTP.

### 4. Запуск
Сервис фронтенда добавляется в `docker-compose.yml` из `frontend/docker-compose.snippet.yml` (один раз):
```yaml
  web:
    build: ./frontend
    ports:
      - "5173:80"
    depends_on:
      - api
```
Затем:
```bash
docker compose up --build -d
```
Таблицы и расширение `pg_trgm` (индексы для поиска) создаются при старте бэкенда автоматически. Миграции (Alembic) не используются.

### 5. Адреса
| Что | Адрес |
|---|---|
| Приложение (frontend) | http://localhost:5173 |
| API, Swagger | http://localhost:8000/docs |
| Mailpit (письма с напоминаниями) | http://localhost:8025 |

Откройте приложение, зарегистрируйтесь, войдите. В «Настройках» укажите email и часовой пояс.

### Полезные команды
```bash
docker compose logs -f api          # логи бэкенда (планировщик, очистка корзины)
docker compose down                 # остановить, данные БД сохраняются
docker compose down -v              # остановить и удалить данные БД
```

## Разработка без Docker для фронтенда
```bash
cd frontend
npm install
npm run dev                         # http://localhost:5173
API_URL=http://localhost:8000 npm run dev   # если бэкенд на другом адресе
```
Запросы `/api/*` проксируются на бэкенд, префикс `/api` отбрасывается.
Сборка: `npm run build`.

## Тестирование API
Скрипт `test_api.sh` (bash + curl + jq) проходит основные сценарии: CRUD, версии и конфликты 409, гонку двух правок, изоляцию пользователей, поиск и фильтры, календарь и повторы, «Ближайшее», напоминания и письма, SSE между вкладками, настройки, корзину.
```bash
# перед запуском очистите Mailpit
curl -s -X DELETE localhost:8025/api/v1/messages
bash test_api.sh | tee test_log.txt
```
Тесты логики повторов: `pytest tests/test_recurrence.py`.

## Архитектура

```
React (nginx)  ──/api──▶  FastAPI  ──▶  PostgreSQL
      ▲                      │  └─ LISTEN/NOTIFY ◀─ другие процессы
      └──── SSE /events ─────┘
                             └─ SMTP ──▶ Mailpit / реальная почта
```
Слои: `routers → services → models` (роутеры только принимают запросы, логика в сервисах).

**Повторяющиеся заметки.** Вхождения не хранятся, а вычисляются на нужный диапазон (`app/recurrence.py`). Исключения для одного вхождения (правка, удаление, перенос) лежат в `note_exceptions`. Правка «это и следующие» разделяет серию: у старой `recurrence_until` становится днём до вхождения, создаётся новая серия.

**Напоминания.** Планировщик раз в 15 секунд находит вхождения, у которых наступило время напоминания (`fire_at <= now < starts_at`). Ровно один раз гарантирует `INSERT ... ON CONFLICT DO NOTHING` в `reminder_deliveries`. Уведомление в браузере создаётся независимо от успеха отправки email.

**Синхронизация между вкладками.** После коммита бэкенд делает `NOTIFY`, каждый процесс слушает канал и рассылает события подключённым клиентам по SSE. Клиент перечитывает данные. Токен для SSE одноразовый и живёт 60 секунд (`POST /events/token`).

**Конфликты правок.** У заметки есть поле `version` (оптимистичная блокировка). Клиент передаёт версию при изменении; при несовпадении сервер отвечает 409 с актуальной версией, а интерфейс предлагает загрузить её или сохранить свои правки поверх. Тихих потерь правок нет.

**Производительность.** Поиск через `ILIKE` с trigram-индексами (`pg_trgm`), пагинация по курсору (keyset) вместо OFFSET, поэтому тысячи заметок не замедляют списки.

**Корзина.** Мягкое удаление (`deleted_at`). Фоновая задача раз в час навсегда удаляет заметки, пролежавшие в корзине больше 30 дней (пачками по 500).

## Допущения
- Время хранится в UTC, показывается в часовом поясе пользователя.
- Пояс повторяющейся серии фиксируется при создании: время серии не «плывёт» при смене пояса в настройках и при переходе на летнее время.
- Месячный повтор 29–31 числа: в коротких месяцах берётся последний день месяца, без дрейфа в следующих месяцах.
- Дата окончания повтора включительна (в поясе серии).
- Напоминание, пропущенное во время простоя сервера, отправляется с опозданием, если заметка ещё не началась; если уже началась, пропускается. Неактивные и удалённые заметки напоминаний не создают.
- Календарь запрашивает не более 100 дней за раз.
- Таблицы создаются через `create_all` вместо миграций.

## Ограничения
- Планировщик защищён от дублей на уровне БД, но не распределён: при нескольких экземплярах API каждый будет опрашивать БД (письма всё равно уйдут один раз).
- SSE доставляет события «не более одного раза»; при разрыве соединения клиент переподключается и перечитывает данные.
- Нет повторных попыток отправки email при сбое SMTP (уведомление в браузере при этом создаётся).
- В «Ближайшем» не реализована подгрузка старых прошедших записей.
- Нет миграций схемы: при изменении моделей в существующей БД нужно вручную менять таблицы или пересоздавать БД (`docker compose down -v`).
